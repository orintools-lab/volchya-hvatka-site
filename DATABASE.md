# База данных проекта «Волчья Хватка»

## 1. Назначение

Документ описывает целевую модель данных production-ready MVP. База данных
хранит каталог, редактируемый контент, заказы, оплату, медиа, административные
учётные записи, сессии и аудит.

Основная СУБД — PostgreSQL. Документ не привязан к синтаксису ORM и является
источником требований для схемы, миграций, репозиториев и тестов.

## 2. Общие соглашения

### 2.1. Идентификаторы

- Основные сущности используют непрогнозируемый строковый UUID или CUID.
- Идентификатор создаётся приложением или базой и после создания не меняется.
- Внешние публичные идентификаторы отделяются от внутренних, если сущность
  показывается пользователю.
- Для заказа используется отдельный человекочитаемый `number`.

### 2.2. Время

- Все даты хранятся с часовым поясом в UTC.
- `created_at` устанавливается только при создании.
- `updated_at` изменяется при каждом содержательном изменении записи.
- Пользовательский интерфейс преобразует время в нужный часовой пояс.

### 2.3. Деньги

- Денежные поля используют фиксированную точность, а не floating point.
- Рекомендуемая точность — до 12 цифр, из них 2 после запятой.
- Валюта MVP — RUB.
- Для расширяемости у заказа и платежа сохраняется трёхбуквенный код валюты.
- Итог заказа рассчитывается на сервере.

### 2.4. Текст и JSON

- Структурированные поля хранятся отдельными колонками.
- JSON используется только для действительно изменяемых структур: UTM,
  безопасный snapshot, provider payload или типизированное значение настройки.
- JSON не заменяет основные связи, статусы и поля поиска.
- Произвольный JavaScript и необработанный пользовательский HTML не хранятся.

### 2.5. Именование

- Таблицы именуются во множественном числе.
- Колонки и ограничения имеют единообразные технические имена.
- Foreign key имеет имя связанной сущности и суффикс `_id`.
- Статусы хранятся как ограниченный набор допустимых значений.

### 2.6. Удаление

Есть три стратегии:

1. **Soft delete** — запись получает `deleted_at`, исключается из обычных запросов
   и может быть восстановлена.
2. **Деактивация** — запись сохраняется, но перестаёт участвовать в публичной или
   прикладной логике через `is_active` или `is_visible`.
3. **Запрет удаления** — исторические и финансовые записи никогда не удаляются
   прикладным интерфейсом.

Soft delete не заменяет признаки публикации и активности.

## 3. Product

Таблица `products` хранит два основных комплекта и дополнительные товары.

### Поля

| Поле | Тип | Обязательность | Назначение |
|---|---|---:|---|
| `id` | строковый UUID/CUID | да | Внутренний первичный ключ. |
| `slug` | строка до 160 символов | да | Уникальный стабильный URL-идентификатор. |
| `category` | статус категории | да | `MAIN` или `ADDITIONAL`. |
| `name` | строка до 200 символов | да | Название товара. |
| `subtitle` | строка до 300 символов | нет | Короткое пояснение. |
| `description` | текст | да | Основное описание. |
| `price` | денежное значение | да | Актуальная цена. |
| `old_price` | денежное значение | нет | Старая цена для корректно обоснованного сравнения. |
| `currency` | строка длиной 3 | да | `RUB` в MVP. |
| `composition` | JSON-массив строк | да | Состав комплекта в заданном порядке. |
| `benefits` | JSON-массив строк | да | Преимущества товара. |
| `image_media_id` | идентификатор | нет | Основное изображение из Media. |
| `badge` | строка до 100 символов | нет | Короткая отметка карточки. |
| `button_label` | строка до 80 символов | да | Подпись основной кнопки. |
| `sort_order` | целое число | да | Порядок внутри категории. |
| `is_active` | boolean | да | Доступность товара для новых заказов. |
| `created_at` | дата и время | да | Дата создания. |
| `updated_at` | дата и время | да | Дата последнего изменения. |
| `deleted_at` | дата и время | нет | Soft delete. |

### Связи

- Product принадлежит одному Media как основному изображению.
- Product имеет много OrderItems.
- При удалении Media ссылка товара не удаляет товар и должна быть предварительно
  очищена или заменена.
- OrderItem сохраняет snapshot товара, поэтому исторический заказ не зависит от
  текущего состояния Product.

### Индексы

- Primary key по `id`.
- Уникальный индекс по нормализованному `slug` только среди неудалённых записей.
- Составной индекс по `category`, `is_active`, `sort_order` среди неудалённых.
- Индекс по `image_media_id`.
- При необходимости административного поиска — индекс по нормализованному
  `name`.

### Ограничения

- `slug` не пустой, в нижнем регистре, состоит из разрешённых URL-символов.
- `price` больше или равна нулю.
- `old_price` отсутствует либо больше `price`.
- `currency` соответствует ISO 4217; для MVP разрешён `RUB`.
- `sort_order` больше или равен нулю.
- `composition` и `benefits` являются массивами строк.
- Активный товар обязан иметь непустые название, описание и цену.

### Soft delete

Product поддерживает soft delete. Удалённый товар:

- не показывается публично;
- не доступен для нового заказа;
- остаётся связанным с историческими позициями;
- может быть восстановлен при отсутствии конфликта slug.

Для временного скрытия используется `is_active`, а не `deleted_at`.

## 4. Orders

Таблица `orders` хранит заказ, данные покупателя, доставку, суммы и жизненный
цикл.

### Поля

| Поле | Тип | Обязательность | Назначение |
|---|---|---:|---|
| `id` | строковый UUID/CUID | да | Внутренний первичный ключ. |
| `number` | строка до 32 символов | да | Уникальный публичный номер заказа. |
| `status` | статус заказа | да | Текущее состояние заказа. |
| `customer_name` | строка до 200 символов | да | ФИО покупателя. |
| `phone` | строка до 32 символов | да | Телефон в нормализованном виде. |
| `email` | строка до 320 символов | да | Email покупателя. |
| `city` | строка до 160 символов | да | Город доставки. |
| `delivery_method` | статус способа доставки | да | Выбранный способ доставки. |
| `delivery_address` | текст | нет | Адрес или пункт получения. |
| `customer_comment` | текст | нет | Комментарий покупателя. |
| `admin_note` | текст | нет | Внутренняя заметка администратора. |
| `subtotal` | денежное значение | да | Сумма позиций. |
| `delivery_price` | денежное значение | да | Стоимость доставки. |
| `discount_total` | денежное значение | да | Сумма применённой скидки; 0 в MVP без скидок. |
| `total` | денежное значение | да | Итог к оплате. |
| `currency` | строка длиной 3 | да | Валюта заказа. |
| `utm` | JSON | нет | Нормализованный набор UTM-меток. |
| `source` | строка до 80 символов | нет | Источник заказа при необходимости. |
| `paid_at` | дата и время | нет | Момент подтверждённой оплаты. |
| `cancelled_at` | дата и время | нет | Момент отмены. |
| `created_at` | дата и время | да | Дата создания. |
| `updated_at` | дата и время | да | Дата изменения. |

### Статусы заказа

| Статус | Значение |
|---|---|
| `NEW` | Заказ создан и ожидает следующего действия. |
| `AWAITING_PAYMENT` | Сформирована попытка оплаты. |
| `PAID` | Оплата подтверждена доверенным callback или mock-провайдером. |
| `PROCESSING` | Заказ принят в обработку. |
| `SHIPPED` | Заказ передан в доставку. |
| `COMPLETED` | Заказ выполнен. |
| `CANCELLED` | Заказ отменён. |

Переходы статусов контролируются сервисом. Нельзя переводить заказ в `PAID`
только по открытию success-страницы.

### Способы доставки

- `CDEK`;
- `RUSSIAN_POST`;
- `COURIER`;
- `PICKUP`;
- `OTHER`.

Набор может уточняться настройками, но сохранённое значение заказа остаётся
неизменным.

### Связи

- Order имеет одну или несколько OrderItems.
- Order имеет ноль или несколько Payments.
- Изменения Order отражаются в AuditLog.

### Индексы

- Primary key по `id`.
- Уникальный индекс по `number`.
- Составной индекс по `status`, `created_at` в обратном хронологическом порядке.
- Индекс по нормализованному `phone`.
- Индекс по нормализованному `email`.
- Индекс по `created_at`.
- Частичный индекс по `paid_at` для оплаченных заказов при необходимости отчётов.

### Ограничения

- Заказ содержит минимум одну позицию.
- `subtotal`, `delivery_price`, `discount_total` и `total` неотрицательны.
- `total` равен `subtotal + delivery_price - discount_total`.
- `currency` одинакова у заказа, позиций и платежей.
- `paid_at` заполнено только для подтверждённой оплаты.
- `cancelled_at` заполнено только для `CANCELLED`.
- Email и телефон сохраняются после серверной нормализации.
- Переходы статусов выполняются атомарно.

### Удаление

Заказы не поддерживают soft delete и не удаляются из административной панели.
Ошибочный или тестовый заказ получает соответствующий статус или служебную
пометку. Удаление допускается только регламентированной операцией очистки
непроизводственных данных.

## 5. OrderItems

Таблица `order_items` хранит позиции и неизменяемый snapshot товара на момент
заказа.

### Поля

| Поле | Тип | Обязательность | Назначение |
|---|---|---:|---|
| `id` | строковый UUID/CUID | да | Первичный ключ. |
| `order_id` | идентификатор | да | Ссылка на Order. |
| `product_id` | идентификатор | нет | Ссылка на исходный Product. |
| `product_name` | строка до 200 символов | да | Snapshot названия. |
| `product_slug` | строка до 160 символов | да | Snapshot slug. |
| `product_snapshot` | JSON | нет | Дополнительный безопасный snapshot состава. |
| `unit_price` | денежное значение | да | Цена единицы на момент заказа. |
| `quantity` | целое число | да | Количество. |
| `total` | денежное значение | да | Стоимость позиции. |
| `currency` | строка длиной 3 | да | Валюта позиции. |
| `created_at` | дата и время | да | Дата создания позиции. |

### Связи

- OrderItem принадлежит одному Order.
- OrderItem может ссылаться на Product.
- При окончательном удалении Product поле `product_id` становится пустым, но
  snapshot позиции сохраняется.
- При удалении Order в тестовой среде позиции удаляются каскадно.

### Индексы

- Primary key по `id`.
- Индекс по `order_id`.
- Индекс по `product_id`.
- При запрете повторяющегося товара в заказе — уникальный индекс по `order_id`,
  `product_id`; если повторение допустимо, ограничение не создаётся.

### Ограничения

- `quantity` — целое число больше нуля.
- `unit_price` и `total` неотрицательны.
- `total` равен `unit_price × quantity`.
- `product_name` и `product_slug` не пустые.
- После создания финансовые поля и snapshot не меняются.

### Удаление

OrderItem не поддерживает самостоятельное удаление и существует столько же,
сколько Order.

## 6. Review

Таблица `reviews` хранит отзывы, созданные и модерируемые администратором.

### Поля

| Поле | Тип | Обязательность | Назначение |
|---|---|---:|---|
| `id` | строковый UUID/CUID | да | Первичный ключ. |
| `author_name` | строка до 160 символов | да | Отображаемое имя. |
| `city` | строка до 160 символов | нет | Город автора. |
| `text` | текст | да | Текст отзыва. |
| `rating` | целое число | да | Оценка от 1 до 5. |
| `image_media_id` | идентификатор | нет | Фото или скриншот из Media. |
| `review_date` | дата | нет | Дата исходного отзыва. |
| `show_on_homepage` | boolean | да | Отбор на главную страницу. |
| `is_visible` | boolean | да | Публичная видимость. |
| `sort_order` | целое число | да | Ручной порядок. |
| `created_at` | дата и время | да | Дата создания записи. |
| `updated_at` | дата и время | да | Дата изменения. |
| `deleted_at` | дата и время | нет | Soft delete. |

### Связи

- Review может иметь один Media.
- Административные изменения Review связаны с AuditLog логически через тип
  сущности и её идентификатор.

### Индексы

- Primary key по `id`.
- Составной частичный индекс по `is_visible`, `show_on_homepage`, `sort_order`
  среди неудалённых.
- Индекс по `review_date`.
- Индекс по `image_media_id`.

### Ограничения

- `rating` находится в диапазоне 1–5.
- `author_name` и `text` не пустые.
- `sort_order` неотрицательный.
- Удалённый отзыв не может быть видимым.
- Отзыв на главной должен одновременно иметь `is_visible = true`.

### Soft delete

Review поддерживает soft delete. Для обычного временного скрытия используется
`is_visible`. Soft delete применяется при удалении из админки и сохраняет
аудиторский контекст.

### Поля

| Поле | Тип | Обязательность | Назначение |
|---|---|---:|---|
| `id` | строковый UUID/CUID | да | Первичный ключ. |
| `question` | строка до 500 символов | да | Вопрос. |
| `answer` | текст | да | Ответ. |
| `sort_order` | целое число | да | Порядок отображения. |
| `is_visible` | boolean | да | Публичная видимость. |
| `created_at` | дата и время | да | Дата создания. |
| `updated_at` | дата и время | да | Дата изменения. |
| `deleted_at` | дата и время | нет | Soft delete. |

### Связи

- FAQ не требует обязательных внешних связей.
- Изменения FAQ фиксируются в AuditLog.

### Индексы

- Primary key по `id`.
- Составной частичный индекс по `is_visible`, `sort_order` среди неудалённых.

### Ограничения

- `sort_order` неотрицательный.
- Удалённая запись не может быть видимой.

### Soft delete

FAQ поддерживает soft delete. Для временного исключения с сайта используется
`is_visible`.

## 8. Media

Таблица `media` хранит метаданные файлов. Содержимое файла располагается в
локальном или S3-совместимом хранилище.

### Поля

| Поле | Тип | Обязательность | Назначение |
|---|---|---:|---|
| `id` | строковый UUID/CUID | да | Первичный ключ. |
| `storage_provider` | статус | да | `LOCAL` или `S3`. |
| `storage_key` | строка до 512 символов | да | Уникальный ключ объекта в хранилище. |
| `original_name` | строка до 255 символов | да | Безопасно сохранённое исходное имя. |
| `mime_type` | строка до 127 символов | да | MIME после серверной проверки. |
| `size_bytes` | большое целое | да | Размер файла. |
| `width` | целое число | нет | Ширина растрового изображения. |
| `height` | целое число | нет | Высота растрового изображения. |
| `checksum` | строка | нет | Хеш содержимого для контроля и дедупликации. |
| `alt_text` | строка до 500 символов | нет | Альтернативный текст. |
| `created_by_user_id` | идентификатор | нет | Администратор, загрузивший файл. |
| `created_at` | дата и время | да | Дата загрузки. |
| `updated_at` | дата и время | да | Изменение метаданных. |
| `deleted_at` | дата и время | нет | Soft delete и начало отложенной очистки. |

### Связи

- Media может использоваться Product.
- Media может использоваться Review.
- Media может использоваться системой редактируемого контента.
- Media может быть загружен User.

Для универсальных связей с контентом предпочтительны явные ссылки в конкретных
таблицах или отдельная таблица назначений, а не массив произвольных ID.

### Индексы

- Primary key по `id`.
- Уникальный индекс по `storage_provider`, `storage_key`.
- Индекс по `created_at`.
- Индекс по `created_by_user_id`.
- Частичный индекс по `deleted_at` для очереди физической очистки.
- Необязательный индекс по `checksum`.

### Ограничения

- `size_bytes` больше нуля и не превышает серверный лимит.
- `width` и `height` либо оба заполнены и положительны, либо оба отсутствуют.
- MIME входит в серверный allowlist.
- `storage_key` не содержит path traversal и не строится из пользовательского
  имени.
- Файл не может физически удаляться, пока существуют активные ссылки.

### Soft delete

Media поддерживает двухфазное удаление:

1. Заполняется `deleted_at`, файл перестаёт выбираться в админке.
2. После проверки ссылок и периода восстановления физический объект удаляется.

## 9. Settings

Таблица `site_settings` хранит типизированные настройки сайта. Секреты в ней не
хранятся.

### Поля

| Поле | Тип | Обязательность | Назначение |
|---|---|---:|---|
| `id` | строковый UUID/CUID | да | Первичный ключ. |
| `key` | строка до 190 символов | да | Стабильный машинный ключ. |
| `group` | строка до 80 символов | да | Раздел админки и назначения. |
| `label` | строка до 200 символов | да | Понятное название. |
| `value_type` | статус типа | да | Тип значения. |
| `value` | JSON | да | Типизированное значение. |
| `is_public` | boolean | да | Разрешено ли отдавать значение публичному UI. |
| `created_at` | дата и время | да | Дата создания. |
| `updated_at` | дата и время | да | Дата изменения. |
| `deleted_at` | дата и время | нет | Soft delete пользовательской настройки. |

### Типы значения

- `STRING`;
- `TEXT`;
- `NUMBER`;
- `BOOLEAN`;
- `URL`;
- `EMAIL`;
- `JSON`;
- `MEDIA_REFERENCE`.

Тип и схема каждого известного ключа дополнительно фиксируются серверным
реестром настроек.

### Связи

- Для `MEDIA_REFERENCE` значение должно ссылаться на существующий Media через
  проверяемую структуру или отдельную ссылочную колонку.
- Каждое изменение настройки фиксируется в AuditLog.

### Индексы

- Primary key по `id`.
- Уникальный индекс по `key` среди неудалённых записей.
- Составной индекс по `group`, `key`.
- Частичный индекс по `is_public` для публичной выборки.

### Ограничения

- `key` соответствует разрешённому формату и известен серверному реестру.
- `value` соответствует `value_type` и Zod-схеме ключа.
- Секретные значения запрещены.
- Публичность определяется серверным реестром и не может произвольно повышаться
  через форму.

### Soft delete

Пользовательские или устаревшие настройки поддерживают soft delete. Обязательные
системные ключи не удаляются: им возвращается значение по умолчанию.

## 10. Users

Таблица `users` хранит административные учётные записи. Аккаунтов покупателей в
MVP нет.

### Поля

| Поле | Тип | Обязательность | Назначение |
|---|---|---:|---|
| `id` | строковый UUID/CUID | да | Первичный ключ. |
| `email` | строка до 320 символов | да | Уникальный нормализованный email. |
| `password_hash` | строка | да | Хеш пароля с параметрами алгоритма. |
| `display_name` | строка до 160 символов | нет | Имя в админке и аудите. |
| `role` | статус роли | да | `ADMIN` в MVP. |
| `status` | статус пользователя | да | Состояние доступа. |
| `failed_login_count` | целое число | да | Последовательные неудачные входы. |
| `locked_until` | дата и время | нет | Временная блокировка. |
| `last_login_at` | дата и время | нет | Последний успешный вход. |
| `password_changed_at` | дата и время | да | Для отзыва старых сессий. |
| `created_at` | дата и время | да | Дата создания. |
| `updated_at` | дата и время | да | Дата изменения. |
| `deleted_at` | дата и время | нет | Soft delete учётной записи. |

### Статусы пользователя

- `ACTIVE` — вход разрешён;
- `DISABLED` — вход запрещён администратором;
- `LOCKED` — вход временно заблокирован защитой;
- `DELETED` — учётная запись выведена из использования.

### Связи

- User имеет много Sessions.
- User может загрузить много Media.
- User имеет много AuditLog.

### Индексы

- Primary key по `id`.
- Уникальный индекс по email без учёта регистра среди неудалённых.
- Индекс по `status`.
- Индекс по `locked_until`.

### Ограничения

- Email хранится в нормализованном виде.
- `password_hash` не может содержать открытый пароль.
- `failed_login_count` неотрицательный.
- Удалённый или отключённый пользователь не создаёт новые сессии.
- Последнего активного администратора нельзя удалить или отключить без создания
  замены.

### Soft delete

User поддерживает soft delete. При удалении:

- статус становится `DELETED`;
- все активные Sessions отзываются;
- email может быть заморожен для аудиторской истории;
- AuditLog сохраняет ссылку либо безопасный snapshot автора.

## 11. Sessions

Таблица `sessions` хранит серверные административные сессии. В cookie передаётся
не сама запись и не открытый токен, а безопасный идентификатор или токен, хеш
которого хранится в базе.

### Поля

| Поле | Тип | Обязательность | Назначение |
|---|---|---:|---|
| `id` | строковый UUID/CUID | да | Первичный ключ. |
| `user_id` | идентификатор | да | Владелец сессии. |
| `token_hash` | строка | да | Уникальный хеш session token. |
| `expires_at` | дата и время | да | Жёсткий срок действия. |
| `last_seen_at` | дата и время | да | Последнее подтверждённое использование. |
| `revoked_at` | дата и время | нет | Момент отзыва. |
| `revoke_reason` | строка до 160 символов | нет | Причина отзыва. |
| `ip_hash` | строка | нет | Минимизированный технический контекст. |
| `user_agent` | строка до 500 символов | нет | Контекст устройства для безопасности. |
| `created_at` | дата и время | да | Дата создания. |

### Статусы сессии

Статус вычисляется из полей:

- `ACTIVE` — не отозвана и не истекла;
- `EXPIRED` — `expires_at` в прошлом;
- `REVOKED` — заполнено `revoked_at`.

Отдельная колонка статуса не нужна, чтобы избежать рассинхронизации.

### Связи

- Session принадлежит одному User.
- При soft delete или отключении User все его Sessions отзываются.

### Индексы

- Primary key по `id`.
- Уникальный индекс по `token_hash`.
- Составной индекс по `user_id`, `expires_at`.
- Частичный индекс по `expires_at` для активных неотозванных сессий.
- Индекс по `revoked_at` для очистки.

### Ограничения

- `expires_at` позже `created_at`.
- `revoked_at` не раньше `created_at`.
- Открытый session token никогда не хранится.
- Истёкшая или отозванная сессия не может быть восстановлена изменением даты.

### Удаление

Sessions не используют soft delete. Сначала они отзываются, затем могут
физически удаляться фоновым регламентом после окончания периода аудита.

## 12. Payments

Таблица `payments` хранит попытки оплаты заказа и нормализованный результат
провайдера.

### Поля

| Поле | Тип | Обязательность | Назначение |
|---|---|---:|---|
| `id` | строковый UUID/CUID | да | Первичный ключ. |
| `order_id` | идентификатор | да | Оплачиваемый Order. |
| `provider` | статус провайдера | да | `MOCK` или `ROBOKASSA`. |
| `provider_payment_id` | строка до 255 символов | нет | Идентификатор у провайдера. |
| `idempotency_key` | строка до 255 символов | да | Ключ создания и повторной обработки. |
| `status` | статус платежа | да | Текущее состояние. |
| `amount` | денежное значение | да | Сумма попытки. |
| `currency` | строка длиной 3 | да | Валюта. |
| `payment_url` | текст | нет | Временный URL перехода, если безопасно хранить. |
| `failure_code` | строка до 100 символов | нет | Нормализованная причина отказа. |
| `failure_message` | строка до 500 символов | нет | Безопасное пояснение. |
| `provider_payload` | JSON | нет | Очищенный технический payload без секретов. |
| `created_at` | дата и время | да | Дата создания попытки. |
| `updated_at` | дата и время | да | Дата изменения. |
| `succeeded_at` | дата и время | нет | Подтверждение успешной оплаты. |

### Статусы платежа

- `PENDING` — попытка создана, окончательного результата нет;
- `SUCCEEDED` — оплата подтверждена;
- `FAILED` — провайдер подтвердил ошибку или отказ;
- `CANCELLED` — попытка отменена;
- `EXPIRED` — срок попытки истёк;
- `REFUNDED` — возврат подтверждён, если возвраты будут подключены.

### Связи

- Payment принадлежит одному Order.
- Один Order может иметь несколько попыток Payment.
- Payment имеет много платёжных событий, если используется отдельный журнал
  provider callbacks.
- Смена Payment на `SUCCEEDED` и Order на `PAID` выполняется одной транзакцией.

### Индексы

- Primary key по `id`.
- Уникальный индекс по `idempotency_key`.
- Уникальный индекс по `provider`, `provider_payment_id`, когда внешний ID
  заполнен.
- Составной индекс по `order_id`, `status`.
- Индекс по `created_at`.
- Частичный индекс по `status`, `created_at` для незавершённых платежей.

### Ограничения

- `amount` больше нуля.
- Сумма и валюта соответствуют Order.
- `succeeded_at` заполнено только для `SUCCEEDED`.
- Успешный Payment не возвращается в `PENDING`.
- Для одного callback должна существовать отдельная защита от повторной
  обработки.
- Provider payload не содержит пароли, подписи и иные секреты.

### Удаление

Payments не поддерживают soft delete и не удаляются прикладным интерфейсом.
Ошибочные и отменённые попытки сохраняются как финансовая история.

## 13. AuditLog

Таблица `audit_logs` является неизменяемым журналом критичных административных и
системных действий.

### Поля

| Поле | Тип | Обязательность | Назначение |
|---|---|---:|---|
| `id` | строковый UUID/CUID | да | Первичный ключ. |
| `actor_user_id` | идентификатор | нет | User, выполнивший действие. |
| `actor_snapshot` | строка до 320 символов | нет | Безопасное имя/email для истории. |
| `action` | строка до 100 символов | да | Тип действия. |
| `entity_type` | строка до 100 символов | да | Тип затронутой сущности. |
| `entity_id` | строковый идентификатор | нет | Идентификатор сущности. |
| `before_data` | JSON | нет | Разрешённый snapshot до изменения. |
| `after_data` | JSON | нет | Разрешённый snapshot после изменения. |
| `request_id` | строка до 100 символов | нет | Корреляция с системным логом. |
| `ip_hash` | строка | нет | Минимизированный технический контекст. |
| `user_agent` | строка до 500 символов | нет | Контекст клиента. |
| `created_at` | дата и время | да | Момент события. |

### Типовые действия

- `LOGIN_SUCCEEDED`;
- `LOGIN_FAILED`;
- `LOGOUT`;
- `CREATE`;
- `UPDATE`;
- `SOFT_DELETE`;
- `RESTORE`;
- `STATUS_CHANGED`;
- `PAYMENT_CONFIRMED`;
- `MEDIA_UPLOADED`;
- `MEDIA_DELETED`;
- `SETTINGS_CHANGED`;
- `EXPORT_CREATED`.

### Связи

- AuditLog может ссылаться на User.
- Ссылка на предметную сущность является логической через `entity_type` и
  `entity_id`, чтобы аудит не удалялся вместе с сущностью.
- При удалении User `actor_user_id` может стать пустым, но `actor_snapshot`
  сохраняется.

### Индексы

- Primary key по `id`.
- Составной индекс по `entity_type`, `entity_id`, `created_at`.
- Составной индекс по `actor_user_id`, `created_at`.
- Индекс по `action`, `created_at`.
- Уникальный или обычный индекс по `request_id` в зависимости от модели
  корреляции.
- Индекс по `created_at` для архивирования.

### Ограничения

- `action` и `entity_type` не пустые.
- Запись после создания не обновляется.
- `before_data` и `after_data` проходят allowlist и не содержат секреты, password
  hash, session token, платёжные подписи и полные чувствительные данные.
- Для пользовательских действий сохраняется actor либо snapshot.

### Удаление

AuditLog не поддерживает soft delete. Записи удаляются или архивируются только
по утверждённой политике хранения данных и отдельной служебной процедуре.

## 14. Дополнительный журнал платёжных событий

Хотя пользовательский перечень выделяет Payments как основную сущность, для
надёжной идемпотентности рекомендуется отдельная таблица `payment_events`.

Она хранит:

- внутренний ID;
- ссылку на Payment;
- внешний ID события;
- тип события;
- очищенный payload;
- результат обработки;
- дату получения;
- дату успешной обработки.

Уникальность по Payment и внешнему ID события не позволяет обработать callback
дважды. События не удаляются через админку.

## 15. Матрица связей

| Родитель | Потомок | Кардинальность | Поведение |
|---|---|---|---|
| Product | OrderItems | один ко многим | Удаление Product не удаляет историю позиции. |
| Media | Products | один ко многим | Удаление Media запрещено при активной ссылке. |
| Media | Reviews | один ко многим | Удаление Media запрещено при активной ссылке. |
| User | Media | один ко многим | User может стать пустым в истории загрузки. |
| User | Sessions | один ко многим | При отключении User сессии отзываются. |
| User | AuditLog | один ко многим | Аудит сохраняется после удаления User. |
| Order | OrderItems | один ко многим | Позиции существуют вместе с заказом. |
| Order | Payments | один ко многим | Все попытки оплаты сохраняются. |
| Payment | PaymentEvents | один ко многим | События обеспечивают идемпотентность. |

## 16. Сводная политика soft delete

| Сущность | Soft delete | Дополнительный признак |
|---|---:|---|
| Product | да | `is_active` для временного скрытия и запрета продажи |
| Orders | нет | Статус `CANCELLED` или служебная пометка |
| OrderItems | нет | Жизненный цикл определяется Order |
| Review | да | `is_visible` и `show_on_homepage` |
| FAQ | да | `is_visible` |
| Media | да | Отложенное физическое удаление |
| Settings | ограниченно | Системные ключи не удаляются |
| Users | да | Статусы `DISABLED`, `LOCKED`, `DELETED` |
| Sessions | нет | Отзыв и последующая регламентная очистка |
| Payments | нет | Финансовый статус |
| AuditLog | нет | Архивирование по политике хранения |

## 17. Конкурентность и целостность

- Создание Order и OrderItems выполняется одной транзакцией.
- Номер заказа создаётся без возможности гонки и защищён уникальным индексом.
- Изменение порядка карточек выполняется транзакционно.
- Успешный Payment и перевод Order в `PAID` атомарны.
- Callback блокируется idempotency key и уникальным ID события.
- Критичные обновления могут использовать optimistic locking через версию записи
  или проверку `updated_at`.
- Репозитории по умолчанию исключают записи с `deleted_at`.
- Административное восстановление проверяет уникальные ключи до снятия
  `deleted_at`.

## 18. Персональные данные и сроки хранения

- Доступ к Orders, Users, Sessions и AuditLog имеет только авторизованный
  администратор.
- В публичные ответы не попадают email, телефон, адрес, внутренние заметки и
  платёжные payload.
- Пароли, открытые session token и секреты интеграций в базе не хранятся.
- Логи и аудит минимизируют IP и пользовательские данные.
- Сроки хранения заказов, платежей, персональных данных, сессий и аудита должны
  быть утверждены владельцем сайта до production-запуска.
- Очистка выполняется отдельной журналируемой процедурой с учётом юридических
  обязанностей владельца.

## 19. Обязательные проверки базы

Минимальный набор интеграционных проверок:

- активные товары выбираются в правильном порядке;
- soft-deleted товары, отзывы и FAQ не попадают в публичные запросы;
- удаление Product не разрушает исторический OrderItem;
- заказ невозможно создать без позиций;
- сервер фиксирует цену в OrderItem;
- суммы заказа согласованы;
- номер заказа уникален при конкурентном создании;
- повторный callback не создаёт повторную оплату;
- успешная оплата атомарно меняет Payment и Order;
- отозванная или истёкшая Session не авторизует администратора;
- soft delete User отзывает его Sessions;
- Media нельзя физически удалить при активной ссылке;
- AuditLog нельзя изменить через прикладной репозиторий;
- Settings не принимают неизвестные ключи и значения неправильного типа.
