# Архитектура проекта «Волчья Хватка»

## 1. Назначение документа

Документ описывает целевую архитектуру production-ready MVP «Волчья Хватка»:
публичного продающего сайта, встроенной административной панели, системы заказов,
оплаты, медиа и редактируемого контента.

Архитектура рассчитана на:

- Next.js с App Router и серверным рендерингом;
- TypeScript в строгом режиме;
- PostgreSQL и Prisma;
- единое приложение без внешней CMS;
- развёртывание на VPS или Node.js-хостинге;
- постепенное подключение внешних интеграций через переменные окружения;
- расширение без переписывания доменной логики.

Документ описывает целевое состояние проекта. Часть каталогов уже существует,
остальные создаются на соответствующих этапах реализации.

## 2. Архитектурные принципы

### 2.1. Разделение ответственности

Каждый слой отвечает только за свой тип задач:

- UI отображает данные и принимает действия пользователя;
- API и server actions определяют транспортные границы;
- сервисы реализуют сценарии приложения;
- репозитории инкапсулируют доступ к данным;
- Prisma отвечает за отображение моделей в PostgreSQL;
- интеграционные адаптеры взаимодействуют с внешними системами.

UI не обращается к Prisma напрямую. Платёжный провайдер не управляет заказом
самостоятельно. Репозиторий не принимает продуктовые решения.

### 2.2. Направление зависимостей

Зависимости направлены от внешних слоёв к внутренним:

1. UI вызывает публичный сценарий приложения.
2. Транспортный слой проверяет входные данные и контекст доступа.
3. Сервис координирует доменную операцию.
4. Репозиторий сохраняет или получает данные.
5. Инфраструктурный адаптер работает с Prisma, файлами, email или оплатой.

Внутренняя бизнес-логика не должна зависеть от React, HTTP, конкретного
платёжного провайдера или способа хранения файлов.

### 2.3. SOLID

**Single Responsibility Principle.** Компонент, сервис, репозиторий и адаптер
имеют одну основную причину для изменения. Например, расчёт заказа отделён от
email-уведомления, а проверка файла — от его физического сохранения.

**Open/Closed Principle.** Новые платёжные провайдеры, способы уведомлений и
хранилища медиа добавляются через новые реализации существующих контрактов без
изменения сценариев заказа.

**Liskov Substitution Principle.** Mock-оплата и Робокасса выполняют единый
контракт платёжного провайдера. Локальное и S3-совместимое медиа-хранилища должны
быть взаимозаменяемы с точки зрения сервисов.

**Interface Segregation Principle.** Контракты остаются небольшими. Чтение
товаров, административное редактирование товаров, создание платежа и обработка
callback не объединяются в один универсальный интерфейс.

**Dependency Inversion Principle.** Сервисы зависят от контрактов репозиториев и
интеграций. Конкретные реализации на Prisma, локальной файловой системе,
Робокассе и SMTP подключаются на инфраструктурной границе.

### 2.4. Сервер как доверенная граница

Все критичные действия выполняются и повторно проверяются на сервере:

- авторизация и проверка роли;
- валидация входных данных;
- получение актуальной цены;
- расчёт итоговой суммы;
- создание заказа;
- изменение статусов;
- проверка платёжного callback;
- проверка MIME, размера и имени файла;
- административное редактирование;
- аудит критичных изменений.

Клиентские проверки улучшают интерфейс, но не считаются защитой.

## 3. Структура каталогов

### Корень проекта

| Каталог или файл | Назначение |
|---|---|
| `src` | Исходный код приложения и серверной логики. |

| `Dockerfile` | Production-сборка и запуск приложения в контейнере. |
| `docker-compose.yml` | Локальный PostgreSQL и production-подобный запуск сервисов. |
| `.env.example` | Полный перечень переменных окружения без реальных секретов. |

| `UI_COMPONENTS.md` | Каталог и назначение UI-компонентов. |
| `ARCHITECTURE.md` | Границы модулей, слоёв и зависимостей проекта. |

### `src/app`

Каталог маршрутов Next.js App Router. Он отвечает за композицию страниц,
маршрутизацию, metadata, HTTP-входы и границы серверного рендеринга. Доменная
логика в нём не размещается.

| Подкаталог | Назначение |
|---|---|
| `src/app/(public)` | Публичная группа маршрутов без изменения URL. Содержит главную, заказ, отзывы и юридические страницы. |
| `src/app/(public)/order` | Страница или маршрутизируемая форма оформления заказа. |
| `src/app/(public)/reviews` | Полный список опубликованных отзывов. |
| `src/app/(public)/privacy` | Политика конфиденциальности из редактируемого контента. |
| `src/app/(public)/offer` | Публичная оферта. |
| `src/app/(public)/delivery` | Условия доставки. |
| `src/app/(public)/payment` | Условия оплаты. |
| `src/app/(public)/returns` | Гарантия и возврат. |
| `src/app/(public)/contacts` | Контакты и реквизиты. |
| `src/app/admin` | Защищённая административная зона. |
| `src/app/admin/login` | Единственный публичный маршрут административной части. |
| `src/app/admin/dashboard` | Сводные показатели и быстрые переходы. |
| `src/app/admin/products` | Управление основными комплектами и дополнительными товарами. |
| `src/app/admin/orders` | Список, фильтры и карточки заказов. |
| `src/app/admin/reviews` | Управление отзывами и их публикацией. |
| `src/app/admin/faq` | Управление вопросами, порядком и видимостью. |
| `src/app/admin/content` | Редактирование секций публичного сайта и юридических текстов. |
| `src/app/admin/media` | Библиотека загруженных файлов. |
| `src/app/admin/settings` | Контакты, реквизиты, доставка, аналитика и интеграционные настройки. |
| `src/app/api` | HTTP API, webhook и технические endpoints. |
| `src/app/api/health` | Healthcheck приложения для Docker и мониторинга. |
| `src/app/api/orders` | Создание заказа и разрешённые операции над ним. |
| `src/app/api/payments` | Начало оплаты, callback, success и fail. |
| `src/app/api/uploads` | Защищённая административная загрузка медиа. |

Страницы получают данные через серверные сценарии. Route handlers отвечают за
HTTP, коды ответа, заголовки, cookies и преобразование ошибок, но не содержат
бизнес-правил.

### `src/components`

Презентационный слой. Компоненты получают типизированные данные и события, не
знают о Prisma и не создают инфраструктурные зависимости.

| Подкаталог | Назначение |
|---|---|
| `src/components/public` | Hero, карточки товаров, отзывы, FAQ, видео, подвал и форма заказа. |
| `src/components/admin` | Таблицы, формы CRUD, административная навигация, фильтры и статусы. |
| `src/components/ui` | Переиспользуемые примитивы: кнопки, поля, диалоги, сообщения, контейнеры и бейджи. |

Компоненты верхнего уровня собирают секции страницы. Примитивы UI не знают о
предметной области. Редактируемые тексты, цены и изображения не хранятся внутри
компонентов.

### `src/lib`

Инфраструктурные утилиты, контракты и адаптеры, которые используются несколькими
модулями.

| Подкаталог | Назначение |
|---|---|
| `src/lib/auth` | Создание и проверка сессии, password hashing, cookies, CSRF и rate limit входа. |
| `src/lib/db` | Единственная конфигурация Prisma Client и управление соединением. |
| `src/lib/payments` | Контракт платёжного провайдера, mock-адаптер и адаптер Робокассы. |
| `src/lib/validation` | Zod-схемы транспортных данных и общие правила нормализации. |
| `src/lib/analytics` | Безопасное подключение Метрики, VK Pixel и типизированные события. |
| `src/lib/media` | Контракт медиа-хранилища, проверка файлов, пути и локальная реализация. |
| `src/lib/integrations` | Общие клиенты внешних систем, если интеграция не относится к более узкому модулю. |
| `src/lib/notifications` | Контракт уведомлений и SMTP/email-реализация. |
| `src/lib/security` | Санитизация HTML, rate limit, безопасные заголовки и вспомогательные проверки. |
| `src/lib/config` | Типизированное чтение и серверная проверка переменных окружения. |

`lib` не должен превращаться в каталог случайных функций. Каждый модуль имеет
ясную инфраструктурную или сквозную ответственность.

### `src/server`

Серверное ядро сценариев приложения. Код из этого каталога не импортируется в
клиентские компоненты.

| Подкаталог | Назначение |
|---|---|
| `src/server/services` | Сценарии приложения и координация операций. |
| `src/server/repositories` | Контракты доступа к данным и реализации на Prisma. |
| `src/server/domain` | Доменные типы, инварианты и чистые правила, когда они сложнее простой CRUD-модели. |
| `src/server/policies` | Правила доступа и разрешения административных действий. |
| `src/server/factories` | Сборка сервисов с конкретными репозиториями и адаптерами. |

Фабрики являются composition root серверной части: именно там выбираются
Prisma-репозиторий, локальное хранилище, mock или реальная оплата и канал
уведомлений.

### `prisma`

| Элемент | Назначение |
|---|---|
| `prisma/schema.prisma` | Каноническое описание таблиц, связей, enum, индексов и ограничений. |
| `prisma/migrations` | Последовательная история изменений структуры PostgreSQL. |
| `prisma/seed.ts` | Идемпотентное заполнение демонстрационным контентом и начальными настройками. |

Seed не содержит production-секретов и вымышленных юридических реквизитов.

### `public`

| Подкаталог | Назначение |
|---|---|
| `public/brand` | Утверждённый мастер-лист и подготовленные варианты логотипа/favicon. |
| `public/images` | Статические изображения, которые поставляются вместе с приложением. |
| `public/icons` | Статические интерфейсные и служебные иконки при необходимости. |

Загружаемые через админку медиа не помещаются в `public`: они проходят через
абстракцию хранилища и каталог `uploads` либо внешний storage.

### `tests`

| Подкаталог | Назначение |
|---|---|
| `tests/unit` | Чистые правила, валидаторы, преобразования и небольшие сервисы. |
| `tests/integration` | Сервисы, Prisma-репозитории, авторизация и API с тестовой базой. |
| `tests/e2e` | Playwright-сценарии публичной покупки и административных операций. |
| `tests/fixtures` | Контролируемые тестовые данные и файлы. |
| `tests/helpers` | Общая настройка окружения и тестовые фабрики. |

Тесты компонентов могут располагаться рядом с компонентами, если это повышает
понятность владения модулем.

### `uploads`

Локальное медиа-хранилище MVP. Каталог монтируется как persistent volume в
Docker, не попадает в Git и не считается частью сборки приложения.

Файлы не получают пользовательское имя как физический путь. Публичный URL,
метаданные и оригинальное имя хранятся отдельно.

### `scripts`

Воспроизводимые служебные операции:

- подготовка бренд-ассетов;
- проверка или миграция медиа;
- резервное копирование;
- контролируемые операции развёртывания.

Скрипты не участвуют в обработке пользовательских запросов.

## 4. Слои приложения

### 4.1. Presentation

Включает страницы App Router и React-компоненты. Отвечает за:

- серверный или клиентский рендеринг;
- доступность и адаптивность;
- отображение loading, error и empty states;
- сбор пользовательского ввода;
- вызов разрешённых серверных сценариев.

Presentation не определяет цену, статус оплаты или права администратора.

### 4.2. Transport

Включает route handlers и server actions. Отвечает за:

- разбор HTTP-запроса или FormData;
- Zod-валидацию;
- извлечение сессии и CSRF-контекста;
- rate limit;
- вызов одного прикладного сценария;
- преобразование результата в HTTP-ответ или состояние формы.

Один транспорт может быть заменён другим без изменения сервисов.

### 4.3. Application

Сервисы реализуют пользовательские сценарии:

- получить содержимое главной страницы;
- создать заказ;
- начать оплату;
- обработать callback;
- войти в административную панель;
- изменить товар;
- опубликовать отзыв;
- обновить FAQ;
- загрузить или удалить медиа;
- обновить настройки;
- экспортировать заказы.

Сервис координирует репозитории и интеграции, контролирует транзакционную границу
и возвращает результат предметного уровня.

### 4.4. Domain

Доменный слой содержит правила, не зависящие от хранения и UI:

- допустимые переходы статуса заказа;
- фиксация цены товара в позиции заказа;
- расчёт subtotal, доставки и total;
- требования к количеству;
- идемпотентность платёжных событий;
- правила видимости и сортировки контента;
- ограничения административных операций.

Простые CRUD-сущности не требуют искусственного усложнения. Доменные объекты
выделяются там, где существуют реальные инварианты.

### 4.5. Infrastructure

Содержит конкретные реализации:

- Prisma и PostgreSQL;
- локальную файловую систему;
- S3-совместимое хранилище в будущем;
- mock-платёж;
- Робокассу;
- SMTP;
- аналитику;
- криптографию, cookies и rate limit.

Инфраструктурные ошибки преобразуются в понятные прикладные ошибки до попадания в
UI.

## 5. UI-архитектура

### 5.1. Server Components по умолчанию

Публичные страницы и административные списки рендерятся серверно, когда им не
нужна браузерная интерактивность. Это уменьшает клиентский JavaScript, улучшает
SEO и предотвращает утечку серверных зависимостей.

Client Components используются только для:

- мобильного меню;
- модальных окон;
- формы заказа;
- интерактивного FAQ;
- загрузки файлов;
- сложных административных форм;
- локальных optimistic-состояний, если они действительно нужны.

### 5.2. Данные UI

UI получает специально подготовленные view models. Они:

- содержат только необходимые поля;
- не раскрывают внутренние и секретные данные;
- преобразуют Decimal и Date в безопасный формат;
- отделяют структуру базы от контракта компонента.

### 5.3. Дизайн-система

Визуальные решения берутся из `DESIGN_SYSTEM.md`, состав компонентов — из
`UI_COMPONENTS.md`, брендовые правила — из `BRAND_GUIDE.md`.

Новый компонент создаётся только тогда, когда существующая композиция не решает
задачу. Редактируемый контент всегда поступает из базы или настроек.

## 6. API

### 6.1. Типы API

В проекте используются:

- server actions для административных форм и тесно связанных с UI операций;
- route handlers для публичного заказа, загрузок, платёжных переходов, callback
  и внешних интеграций;
- server-side service calls для рендеринга страниц.

### 6.2. Общий конвейер запроса

Каждый изменяющий запрос проходит:

1. проверку метода и content type;
2. rate limit;
3. аутентификацию и авторизацию, если требуются;
4. CSRF-защиту для браузерных административных операций;
5. Zod-валидацию;
6. вызов сервиса;
7. безопасное преобразование ошибки;
8. аудит критичной операции.

### 6.3. Ошибки

Публичный API не возвращает stack trace, SQL, секреты и внутренние идентификаторы
интеграций. Ошибки делятся на:

- некорректный ввод;
- отсутствие авторизации;
- недостаток прав;
- сущность не найдена;
- конфликт или повторная операция;
- временная ошибка интеграции;
- внутренняя ошибка.

## 7. Сервисы

Каждый сервис ориентирован на сценарий, а не на таблицу.

### ContentQueryService

Собирает главную страницу из товаров, секций, отзывов, FAQ и настроек. Возвращает
готовую безопасную модель представления и не раскрывает скрытый контент.

### ProductAdminService

Создаёт и редактирует товары, проверяет slug, цены, порядок и активность. Пишет
аудит критичных изменений.

### OrderService

Получает актуальный товар на сервере, рассчитывает сумму, создаёт заказ и
зафиксированные позиции, инициирует уведомления. Не доверяет цене от клиента.

### OrderAdminService

Возвращает список и карточку заказа, контролирует переходы статусов, заметки и
CSV-экспорт.

### PaymentService

Создаёт платёж через выбранный provider, сохраняет попытку, обрабатывает
идемпотентный callback и переводит заказ в `PAID` только после успешной проверки.

### MediaService

Проверяет разрешение операции, MIME, фактический формат и размер, генерирует
безопасное имя, сохраняет файл через storage и фиксирует метаданные.

### SettingsService

Читает и обновляет разрешённые настройки по типизированному реестру ключей.
Секретные значения не отдаёт в публичный UI.

### AuthService

Проверяет административные credentials, создаёт и отзывает сессии, применяет
rate limit и фиксирует события безопасности.

### NotificationService

Формирует уведомления покупателю и администратору на основе результата заказа.
Ошибка email не откатывает уже созданный заказ, но журналируется и допускает
повторную отправку.

## 8. Репозитории

Репозитории предоставляют узкие интерфейсы хранения:

- ProductRepository;
- ContentRepository;
- ReviewRepository;
- FaqRepository;
- SettingsRepository;
- OrderRepository;
- PaymentRepository;
- MediaRepository;
- AdminUserRepository;
- AuditRepository.

Они отвечают за:

- запросы и сохранение;
- пагинацию и фильтрацию;
- транзакционное участие;
- преобразование persistence-модели в внутренний тип.

Они не отвечают за:

- HTTP;
- React;
- проверку прав пользователя;
- отправку email;
- выбор следующего статуса;
- расчёт бизнес-суммы.

Prisma-реализации располагаются рядом с контрактами в
`src/server/repositories`, но именуются явно. Для чтения сложной главной страницы
допустим специализированный query-репозиторий вместо серии универсальных CRUD-
вызовов.

## 9. Prisma и PostgreSQL

### 9.1. Основные сущности

- `AdminUser` — административная учётная запись;
- `Product` — основные комплекты и дополнительные товары;
- `Review` — отзывы и признаки публикации;
- `FaqItem` — FAQ, порядок и видимость;
- `ContentBlock` — редактируемые секции и юридические тексты;
- `SiteSetting` — структурированные настройки сайта;
- `Media` — метаданные загруженных файлов;
- `Order` — покупатель, доставка, суммы и статус;
- `OrderItem` — зафиксированные название, slug, цена и количество;
- `Payment` — попытка оплаты и идемпотентность;
- `PaymentEvent` — журнал callback и событий провайдера;
- `AuditLog` — критичные действия администратора.

### 9.2. Транзакции

Транзакция обязательна для:

- создания заказа и его позиций;
- успешной фиксации платёжного события и смены статуса заказа;
- операций, где изменение сущности и аудит должны быть атомарны;
- согласованной перестановки сортируемых элементов.

Внешний HTTP-вызов не удерживает открытую транзакцию дольше необходимого.

### 9.3. Денежные значения

Деньги хранятся в Decimal с фиксированной точностью. Клиент не передаёт
авторитетную итоговую сумму. Позиция заказа сохраняет цену на момент оформления,
поэтому последующее изменение товара не изменяет историю заказа.

### 9.4. Миграции и резервирование

Изменения схемы выполняются только миграциями. В production применяется
`migrate deploy`. Резервное копирование PostgreSQL является частью операционной
инфраструктуры и проверяется восстановлением, а не только наличием архивов.

## 10. Система медиа

### 10.1. Контракт хранилища

Медиа-сервис зависит от небольшого storage-контракта:

- сохранить поток;
- получить публичный или защищённый URL;
- удалить объект;
- проверить существование.

MVP использует локальную реализацию. Переход на S3-совместимое хранилище не
меняет UI, API и прикладные сервисы.

### 10.2. Загрузка

Загрузка доступна только авторизованному администратору. Сервер:

- ограничивает размер через `MAX_UPLOAD_MB`;
- проверяет заявленный MIME и сигнатуру;
- разрешает только утверждённые форматы;
- создаёт непредсказуемое безопасное имя;
- исключает path traversal;
- сохраняет размер, тип, оригинальное имя, путь и alt-текст;
- при необходимости создаёт оптимизированные варианты изображения.

### 10.3. Выдача

Локальные загруженные файлы отдаются через контролируемый маршрут или отдельный
статический media endpoint. Пользовательские файлы не исполняются как JavaScript
и не интерпретируются как серверные шаблоны.

### 10.4. Удаление

Перед физическим удалением проверяется использование файла товарами, отзывами и
контентом. Возможна двухфазная стратегия: сначала скрытие или пометка, затем
фоновая очистка неиспользуемых объектов.

## 11. Система настроек и контента

### 11.1. Разделение

`ContentBlock` хранит редактируемое содержимое страниц: заголовки, тексты,
структурированные списки, видео и юридические материалы.

`SiteSetting` хранит конфигурацию сайта: контакты, реквизиты, ссылки, параметры
доставки и разрешённые публичные идентификаторы аналитики.

Секреты платёжных и SMTP-интеграций хранятся только в environment и не
редактируются через обычную админку.

### 11.2. Реестр ключей

Настройки и контент используют контролируемый реестр известных ключей. Для
каждого ключа определяются:

- тип;
- значение по умолчанию;
- публичность;
- правила валидации;
- административная подпись;
- допустимость HTML;
- необходимость аудита.

Это предотвращает превращение системы настроек в нетипизированное хранилище.

### 11.3. HTML

Произвольный JavaScript запрещён. Если поле поддерживает форматированный текст,
HTML очищается по allowlist на сервере. Для большинства полей предпочтительны
структурированные данные и обычный текст.

## 12. Авторизация и безопасность

### 12.1. Модель доступа

В MVP существует административная роль. Публичный пользователь не создаёт
аккаунт. Все маршруты `/admin`, кроме `/admin/login`, требуют действующей
серверной сессии.

### 12.2. Credentials

Администратор входит по email и паролю. Пароль никогда не хранится открытым
текстом. Начальная учётная запись создаётся безопасным bootstrap-процессом или
seed-командой из environment.

### 12.3. Сессия

Сессия использует:

- `httpOnly` cookie;
- `secure` в production;
- подходящий `sameSite`;
- ограниченный срок жизни;
- ротацию или отзыв;
- секрет из `AUTH_SECRET`.

Middleware может выполнять раннее перенаправление, но окончательная проверка
доступа повторяется в серверном сценарии.

### 12.4. Защита

- CSRF для изменяющих браузерных запросов;
- rate limit для входа, заказа и чувствительных endpoints;
- Zod для всех внешних данных;
- безопасные HTTP-заголовки;
- отсутствие секретов в клиентском bundle;
- нейтральные сообщения при ошибке входа;
- аудит входа и критичных административных изменений.

## 13. Система оплаты

### 13.1. PaymentProvider

Прикладной сервис зависит от общего контракта провайдера. Реализации:

- mock для разработки и работы до подключения реальных ключей;
- Robokassa для production.

Provider отвечает за протокол конкретной системы: создание параметров,
подписание, проверку callback и нормализацию результата. Он не меняет заказ
напрямую.

### 13.2. Платёжный процесс

1. Покупатель создаёт заказ.
2. Сервер фиксирует позиции и итог.
3. PaymentService создаёт запись попытки с idempotency key.
4. Provider формирует переход или mock-результат.
5. Callback проходит криптографическую проверку.
6. Событие сохраняется один раз.
7. В одной транзакции платёж и заказ переходят в успешный статус.
8. Повторный callback возвращает успешный безопасный ответ без повторной
   обработки.

### 13.3. Безопасность Робокассы

- пароли берутся только из environment;
- тестовый режим определяется конфигурацией;
- подпись проверяется на сервере;
- сумма callback сравнивается с сохранённой суммой;
- идентификатор заказа проверяется;
- callback идемпотентен;
- входной payload журналируется без секретов;
- success URL не считается доказательством оплаты.

## 14. Интеграции

### 14.1. Email

SMTP-адаптер отправляет:

- подтверждение заявки покупателю;
- уведомление о новом заказе администратору;
- платёжное подтверждение при необходимости.

Контракт уведомлений позволяет позже добавить Telegram без изменения
OrderService.

### 14.2. Аналитика

Яндекс Метрика и VK Pixel подключаются только при наличии идентификаторов.
События имеют типизированные имена из ТЗ. Интеграция не должна блокировать
оформление заказа и не загружается без настройки.

UTM-метки нормализуются и сохраняются вместе с заказом без влияния на расчёт.

### 14.3. Видео

Видео-модуль нормализует поддерживаемые источники YouTube, VK Video, Rutube и
прямой mp4 URL. Тяжёлый player не загружается до действия пользователя.

### 14.4. Будущие интеграции

Новые интеграции добавляются отдельными адаптерами. Сервис использует
минимальный контракт и не зависит от SDK конкретного поставщика.

## 15. Административная панель

### 15.1. Общая архитектура

Админка является частью того же Next.js-приложения. Она использует общий UI-
фундамент, но отдельную навигацию, layouts и политики доступа.

Это не page builder. Каждый раздел представляет понятные CRUD-формы для
определённой сущности или группы строго типизированных настроек.

### 15.2. Разделы

**Dashboard:** сводка заказов, статусов и быстрые переходы без тяжёлой аналитики.

**Products:** основные и дополнительные товары, цены, изображения, состав,
преимущества, badge, порядок и активность.

**Orders:** поиск, фильтры, список, карточка, статусы, заметки и CSV.

**Reviews:** создание, редактирование, удаление, сортировка, скрытие, избранность
и загрузка скриншотов.

**FAQ:** вопросы, ответы, порядок и видимость.

**Content:** hero, показатели доверия, видео, преимущества, подвал и юридические
страницы.

**Media:** загрузка, preview, alt-текст, использование и удаление.

**Settings:** контакты, реквизиты, социальные ссылки, доставка и публичные
настройки аналитики.

### 15.3. Изменение данных

Административная форма:

1. загружает текущую view model;
2. отправляет только разрешённые поля;
3. проходит серверную Zod-валидацию;
4. проверяет сессию и policy;
5. вызывает административный сервис;
6. сохраняет изменение и аудит;
7. обновляет соответствующий cache tag;
8. возвращает безопасный результат форме.

### 15.4. Адаптивность

Административные таблицы на мобильном превращаются в карточки или используют
контролируемый горизонтальный скролл. Все основные действия имеют зону не менее
48 px и доступны без hover.

## 16. Кэширование и актуальность

Публичные данные могут кэшироваться по доменным тегам:

- products;
- content;
- reviews;
- faq;
- settings.

После административного изменения инвалидируется только связанный тег. Заказы,
платежи, сессии и административные списки не используют публичный статический
кэш.

Кэширование не должно быть источником авторитетной цены при создании заказа:
OrderService получает актуальные данные на серверной стороне.

## 17. Наблюдаемость и аудит

Структурированные логи содержат:

- request/correlation ID;
- тип операции;
- обезличенный контекст;
- продолжительность;
- результат;
- безопасное описание ошибки.

Не журналируются пароли, платёжные секреты, session cookie и полные чувствительные
данные покупателя.

`AuditLog` фиксирует администратора, действие, сущность, допустимые before/after
данные, время и технический контекст. Аудит не заменяет системные логи.

## 18. Тестовая архитектура

### Unit

Проверяют доменные правила, Zod-схемы, расчёты, переходы статусов и преобразование
данных без базы и сети.

### Integration

Проверяют Prisma-репозитории и сервисы на отдельной тестовой PostgreSQL:

- получение товаров;
- вход администратора;
- защиту `/admin`;
- изменение цены;
- создание заказа;
- отображение заказа в админке;
- mock-оплату;
- идемпотентный callback;
- скрытие FAQ и отзывов.

### E2E

Playwright проверяет критичный пользовательский путь на desktop и mobile:

- главная открывается;
- комплект выбирается;
- форма валидируется;
- заказ создаётся;
- mock-оплата завершается;
- результат виден в админке.

## 19. Развёртывание

Production-контур включает:

- контейнер приложения;
- PostgreSQL;
- persistent volume для локальных uploads;
- миграции перед запуском новой версии;
- healthcheck;
- HTTPS на reverse proxy;
- резервное копирование базы и медиа;
- безопасную передачу environment;
- ротацию логов и мониторинг доступности.

Приложение собирается один раз и получает конфигурацию среды при запуске.
Production-секреты не попадают в Docker image.

## 20. Правила развития архитектуры

- Не обращаться к Prisma из React-компонентов и route handlers напрямую.
- Не размещать бизнес-правила в Zod-схемах, UI или платёжном адаптере.
- Не создавать универсальные «god services» и репозитории.
- Не добавлять абстракцию без реальной точки вариативности или тестовой границы.
- Не хранить редактируемый контент в компонентах.
- Не хранить секреты в базе настроек или клиентском коде.
- Не связывать статус заказа с фактом перехода на success URL.
- Не удалять медиа без проверки ссылок на него.
- Каждая новая интеграция получает узкий контракт и адаптер.
- Каждая критичная операция имеет валидацию, проверку доступа, журналирование и
  тест.
- Изменение архитектурной границы сопровождается обновлением этого документа.
