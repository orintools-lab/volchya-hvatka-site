# Roadmap — «Волчья Хватка»

## 1. Назначение

Документ разбивает развитие проекта на последовательные продуктовые этапы:

MVP → Оплата → Доставка → SEO → Личный кабинет → Промокоды → Склад → CRM →
Telegram → Международная версия → ORIN

Этапы расположены по зависимостям. Каждый следующий блок строится на уже
работающем и измеряемом предыдущем. Новый функционал не должен ухудшать основной
путь:

Главная → Комплект → Форма → Оплата → Спасибо → Письмо → Админка → Обработка →
Отправка → Получение.

## 2. Принципы развития

### Сначала продажи, затем автоматизация

Первый приоритет — надёжно принять заказ, оплату и обработать отправку. Склад,
CRM и дополнительные каналы не создаются до появления устойчивого операционного
процесса.

### Один этап — один измеримый результат

Этап считается завершённым не по количеству созданных экранов, а когда работает
сквозной пользовательский или операционный сценарий.

### Никаких скрытых зависимостей

Перед началом этапа должны быть готовы:

- данные;
- процессы;
- юридические решения;
- доступы к внешним системам;
- ответственный владелец процесса;
- критерии успешности.

### Расширение через существующие контракты

- новый платёжный provider подключается через PaymentProvider;
- новая доставка — через DeliveryProvider;
- новый канал уведомлений — через NotificationProvider;
- новое хранилище — через MediaStorage;
- новый рынок — через locale, currency и market configuration;
- новый продукт экосистемы не копирует общую инфраструктуру без причины.

### MVP не раздувается

Функция не включается в текущий этап только потому, что она может пригодиться в
будущем. Для каждого расширения требуется реальная задача и критерий результата.

## 3. Обзор этапов

| Этап | Главный результат | Зависит от |
|---|---|---|
| 1. MVP | Сайт принимает заказ и позволяет обработать его вручную | Базовая инфраструктура |
| 2. Оплата | Реальные платежи проходят безопасно и идемпотентно | MVP |
| 3. Доставка | Отправление оформляется и отслеживается системно | Заказы и оплата |
| 4. SEO | Сайт получает устойчивую техническую и контентную видимость | Стабильная публичная часть |
| 5. Личный кабинет | Покупатель видит свои заказы и доступы | Стабильная идентификация заказов |
| 6. Промокоды | Управляемые скидки применяются без ошибок в расчётах | Оплата и личный кабинет необязателен |
| 7. Склад | Остатки и резервирование связаны с заказами | Стабильный каталог и статусы |
| 8. CRM | История клиента и работа менеджера объединены | Заказы, коммуникации и склад |
| 9. Telegram | Операционные уведомления и разрешённые действия доступны в Telegram | CRM и NotificationProvider |
| 10. Международная версия | Несколько языков, валют и рынков работают из общей платформы | Стабильная доменная модель |
| 11. ORIN | Отдельный продукт подключён к экосистеме по утверждённому брифу | Общая платформа и отдельное ТЗ |

## 4. Этап 1 — MVP

### Цель

Запустить production-ready сайт, который продаёт два основных комплекта,
сохраняет заказы и позволяет владельцу обрабатывать их через простую админку.

### Публичная часть

- адаптивная главная;
- Header и Hero;
- показатели доверия;
- два основных комплекта;
- видео;
- преимущества;
- отзывы;
- FAQ;
- дополнительные товары;
- Footer;
- юридические страницы;
- форма заказа;
- страница благодарности.

### Контент

- редактируемые товары;
- редактируемые секции;
- отзывы;
- FAQ;
- контакты;
- реквизиты;
- юридические тексты;
- медиа;
- SEO-поля базового уровня.

### Админка

- защищённый вход;
- Dashboard;
- товары;
- контент;
- отзывы;
- FAQ;
- заказы;
- файлы;
- настройки;
- AuditLog для критичных изменений.

### Заказы

- создание Order и OrderItems;
- snapshot товара и цены;
- статусы;
- внутренние заметки;
- CSV;
- email покупателю;
- email администратору;
- ручная обработка;
- ручная фиксация отправки и получения.

### Оплата в MVP

Используется mock provider. Архитектура реальной оплаты уже заложена, но реальные
списания не выполняются без production-реквизитов и проверки callback.

### Инфраструктура

- PostgreSQL;
- Prisma;
- миграции;
- seed;
- локальное MediaStorage;
- Docker;
- healthcheck;
- environment validation;
- backup procedure;
- lint;
- typecheck;
- unit и integration tests;
- Playwright для основного пути.

### Не входит в MVP

- реальная Робокасса;
- интеграция со службой доставки;
- аккаунт покупателя;
- промокоды;
- склад;
- CRM;
- Telegram;
- мультиязычность;
- ORIN.

### Критерии завершения

- сайт работает на desktop и mobile;
- из базы показываются два основных комплекта;
- администратор меняет товар и публичный контент;
- покупатель создаёт заказ;
- заказ появляется в админке;
- mock-оплата переводит заказ в `PAID`;
- заказ проходит `PROCESSING`, `SHIPPED`, `COMPLETED`;
- письма отправляются или безопасно ставятся на повтор;
- юридические страницы заполнены владельцем;
- секретов в репозитории нет;
- production Docker запускается;
- обязательные проверки проходят.

## 5. Этап 2 — Реальная оплата

### Цель

Подключить реальные платежи без изменения пользовательского пути и без риска
двойного подтверждения.

### Объём

- Robokassa как production PaymentProvider;
- формирование подписи;
- переход на платёжную страницу;
- success и fail routes;
- защищённый callback;
- проверка суммы и номера заказа;
- idempotency;
- Payment Events;
- повторные попытки;
- диагностика в админке;
- уведомление об успешной оплате;
- разделение test и production mode.

### Административный интерфейс

- список платежей;
- фильтр по provider и status;
- карточка Payment;
- timeline callbacks;
- связь с Order;
- безопасные ошибки;
- состояние настройки provider;
- отсутствие ручного поля «сделать оплачено».

### Операционные задачи

- заключить договор с provider;
- получить production-реквизиты;
- определить юридические данные чека;
- проверить требования 54-ФЗ и фискализации с владельцем и специалистом;
- определить возвраты;
- настроить мониторинг callback;
- провести реальные тестовые платежи минимальной суммы.

### Критерии завершения

- успешный платёж подтверждается callback;
- success URL не меняет статус;
- неверная подпись отклоняется;
- неверная сумма отклоняется;
- повторный callback безопасен;
- неуспешный платёж можно повторить;
- заказ и платёж изменяются атомарно;
- финансовые события видны в логах;
- тестовый и production-контуры разделены.

## 6. Этап 3 — Доставка

### Цель

Снизить ручную работу при оформлении отправления и дать покупателю достоверную
информацию о доставке.

### Подэтап 3.1 — Нормализация ручной доставки

- типизированные способы доставки;
- стоимость или правило расчёта;
- обязательность адреса;
- snapshot способа и цены в Order;
- трек-номер;
- дата отправки;
- ссылка отслеживания;
- письмо об отправке;
- статус `SHIPPED`;
- фиксация получения администратором.

Этот подэтап может быть частью MVP, если выполняется без внешнего API.

### Подэтап 3.2 — DeliveryProvider

- общий контракт провайдера;
- расчёт доступных вариантов;
- пункты выдачи;
- создание отправления;
- получение этикетки;
- tracking status;
- webhook или плановая синхронизация;
- отмена отправления;
- безопасное логирование.

Конкретный provider выбирается владельцем после анализа тарифов и географии.

### Интерфейс покупателя

- выбор доступного способа;
- стоимость;
- срок как диапазон, если provider его подтверждает;
- выбор пункта или адреса;
- понятное состояние ошибки provider;
- возможность оформить заказ при временном сбое по разрешённому fallback.

### Админка

- очередь готовых к отправке;
- создание отправления;
- печать этикетки;
- трек-номер;
- статус доставки;
- проблемные отправления;
- ручное исправление только с аудитом.

### Критерии завершения

- стоимость доставки зафиксирована в заказе;
- отправление не создаётся дважды;
- трек-номер сохраняется;
- покупатель получает уведомление;
- provider error не теряет заказ;
- статусы provider не подменяют Order status без нормализации;
- ручной fallback документирован.

## 7. Этап 4 — SEO

### Цель

Сделать сайт технически индексируемым, быстрым и управляемым для поискового
продвижения.

### Техническое SEO

- server rendering;
- metadata;
- title templates;
- descriptions;
- canonical;
- Open Graph;
- favicon;
- sitemap;
- robots;
- корректные status codes;
- отсутствие индексирования `/admin`, API и технических страниц;
- человекочитаемые URL;
- внутренние ссылки;
- breadcrumbs на вложенных страницах;
- оптимизация изображений;
- Core Web Vitals;
- Lighthouse не ниже ориентиров из ТЗ.

### Structured Data

- Organization;
- Product;
- FAQPage;
- BreadcrumbList при наличии;
- Offer только с актуальными данными;
- отсутствие скрытого FAQ в schema.org.

### Контентная основа

- отдельные indexable страницы товаров при подтверждённой необходимости;
- качественные заголовки;
- уникальные descriptions;
- тексты без keyword stuffing;
- полезный FAQ;
- alt-тексты;
- юридически корректные данные организации.

### Инструменты

- Яндекс Вебмастер;
- Google Search Console при работе с соответствующим рынком;
- Яндекс Метрика;
- мониторинг 404 и server errors;
- журнал изменений SEO-полей.

### Критерии завершения

- публичные страницы индексируются корректно;
- технические страницы закрыты;
- sitemap и robots валидны;
- structured data проходит проверку;
- canonical не конфликтует;
- изображения оптимизированы;
- Lighthouse соответствует ориентирам;
- владелец может редактировать разрешённые SEO-поля;
- поисковые ошибки мониторятся.

## 8. Этап 5 — Личный кабинет

### Условие начала

Личный кабинет создаётся только после подтверждения, что покупателям нужен
регулярный доступ к заказам, курсам или повторным покупкам. Если достаточно
email-ссылок, сложная учётная запись откладывается.

### Цель

Дать покупателю безопасный доступ к своим заказам, доставке и обучающим
материалам.

### Идентификация

Предпочтительный первый вариант:

- вход по email;
- одноразовая magic link;
- ограниченный срок;
- защищённая сессия.

Пароль добавляется только при подтверждённой необходимости.

### Разделы

- обзор;
- мои заказы;
- карточка заказа;
- статус оплаты;
- статус доставки;
- доступные курсы;
- профиль;
- контакты;
- активные сессии;
- выход.

### Доступ к курсу

- entitlement создаётся после подтверждённой оплаты;
- доступ связан с конкретным продуктом;
- отмена или возврат обрабатываются отдельным правилом;
- URL урока не является единственной защитой;
- история доступа не меняет финансовую историю заказа.

### Безопасность

- покупатель видит только собственные данные;
- защита от перебора;
- ограниченные magic links;
- отзыв сессии;
- аудит критичных действий;
- минимизация персональных данных;
- процесс удаления или выгрузки данных после юридического анализа.

### Критерии завершения

- покупатель безопасно входит;
- не видит чужой заказ;
- видит актуальную оплату и доставку;
- доступ к курсу открывается только по правилу;
- email-ссылка одноразовая;
- сессии можно отозвать;
- mobile UX покрыт E2E.

## 9. Этап 6 — Промокоды

### Цель

Добавить управляемые скидки без нарушения расчётов, оплаты и отчётности.

### Модель промокода

- code;
- тип скидки;
- значение;
- валюта для фиксированной скидки;
- начало и окончание;
- общий лимит;
- лимит на покупателя;
- минимальная сумма;
- разрешённые Product;
- активность;
- stackability;
- служебное описание.

### Типы скидки

- процент;
- фиксированная сумма;
- бесплатная доставка, если процесс доставки это поддерживает.

### Правила

- сервер является единственным источником расчёта;
- скидка фиксируется snapshot в Order;
- скидка не делает итог отрицательным;
- лимит использования защищён от гонки;
- изменение промокода не меняет старые заказы;
- promo code не раскрывает персональные сегменты;
- применение и отмена аудитируются.

### Публичный интерфейс

- компактное необязательное поле;
- явная кнопка применения;
- понятный результат;
- показ скидки в расчёте;
- корректное удаление промокода;
- сохранение введённых данных формы.

### Админка

- список;
- фильтры;
- создание;
- статистика использования;
- активация;
- деактивация;
- ограниченное редактирование после использования;
- soft delete.

### Критерии завершения

- расчёт выполняется сервером;
- лимиты соблюдаются при конкуренции;
- Payment получает итог после скидки;
- Order хранит snapshot;
- невалидный код не раскрывает внутренние правила;
- возвраты учитывают скидку.

## 10. Этап 7 — Склад

### Условие начала

Склад добавляется, когда ручного контроля остатков недостаточно и определён
фактический процесс производства, комплектации и списания.

### Цель

Не продавать недоступный товар и видеть движение изделий.

### Основные сущности

- SKU;
- склад или место хранения;
- остаток;
- резерв;
- доступное количество;
- движение;
- инвентаризация;
- причина корректировки;
- поставка или производство;
- списание.

### Связь с Product

Product может состоять из одного или нескольких SKU. Комплект резервирует
необходимое количество каждого элемента.

### Жизненный цикл

1. Заказ создаётся.
2. Остаток проверяется.
3. Товар резервируется по утверждённому правилу.
4. После оплаты резерв подтверждается.
5. При отмене резерв освобождается.
6. При отправке происходит списание.
7. Возврат оформляется отдельным движением.

Точный момент резерва определяется бизнес-процессом до реализации.

### Админка

- остатки;
- низкий остаток;
- движения;
- резервы;
- инвентаризация;
- корректировка с обязательной причиной;
- история SKU;
- связь с Order.

### Критерии завершения

- доступный остаток не становится отрицательным без отдельного разрешения;
- резерв защищён транзакцией;
- отмена освобождает резерв;
- отправка списывает товар один раз;
- каждое движение имеет основание;
- ручная корректировка аудитируется;
- комплект корректно влияет на компоненты SKU.

## 11. Этап 8 — CRM

### Условие начала

CRM создаётся после формирования реальной команды и повторяемого процесса работы
с клиентами. Она не должна быть копией универсальных CRM «на всякий случай».

### Цель

Объединить историю клиента, заказов, коммуникаций и задач менеджера.

### Профиль клиента

- контакты;
- согласия;
- заказы;
- оплаты;
- доставка;
- курсы;
- обращения;
- заметки;
- задачи;
- сегменты;
- источник;
- история изменений.

### Дедупликация

Клиенты сопоставляются по нормализованным контактам с безопасной ручной
проверкой. Автоматическое объединение не должно терять историю.

### Задачи

- тип;
- ответственный;
- срок;
- приоритет;
- статус;
- связь с клиентом или заказом;
- результат.

### Коммуникации

- email;
- телефон как вручную зафиксированное событие;
- Telegram после соответствующего этапа;
- системные уведомления.

Содержание личных коммуникаций хранится только при наличии правового основания и
понятной политики хранения.

### Админка

- клиенты;
- карточка клиента;
- сегменты;
- задачи;
- timeline;
- фильтры;
- экспорт с аудитом;
- разрешения доступа при появлении нескольких сотрудников.

### Критерии завершения

- нет дублирующей истории;
- менеджер видит связанный контекст;
- задачи имеют владельца и срок;
- экспорт контролируется;
- персональные данные защищены;
- сегменты не влияют на пользователя без понятного основания;
- CRM не меняет финансовые факты заказа.

## 12. Этап 9 — Telegram

### Цель

Добавить Telegram как дополнительный канал оперативных уведомлений и
ограниченных административных действий.

### Подэтап 9.1 — Уведомления администратору

- новый заказ;
- успешная оплата;
- проблемный платёж;
- заказ требует обработки;
- ошибка интеграции;
- низкий остаток после появления склада.

### Подэтап 9.2 — Безопасные действия

Возможны только явно разрешённые команды:

- открыть карточку заказа;
- подтвердить получение уведомления;
- назначить заказ на себя при появлении команды;
- добавить короткую заметку;
- перейти в защищённую админку.

Изменение финансового статуса и опасные действия внутри чата запрещены.

### Подэтап 9.3 — Покупательские уведомления

Добавляются только при явном согласии пользователя:

- подтверждение заказа;
- подтверждение оплаты;
- отправка;
- доставка.

### Безопасность

- webhook secret;
- allowlist административных аккаунтов;
- связь Telegram ID с User;
- отсутствие персональных данных в общих чатах;
- rate limit;
- AuditLog;
- отзыв доступа;
- минимальные права bot token.

### Критерии завершения

- email остаётся независимым каналом;
- Telegram error не теряет заказ;
- неавторизованный аккаунт не получает данные;
- webhook проверяется;
- команды идемпотентны;
- критичные действия ведут в защищённую админку.

## 14. Этап 11 — ORIN

## 16. Правила приоритизации

Функция поднимается выше в roadmap, если она:

- блокирует получение денег;
- предотвращает потерю заказа;
- снижает финансовый или юридический риск;
- устраняет регулярную ручную ошибку;
- нужна значительной доле покупателей;
- имеет измеримый эффект.

Функция откладывается, если она:

- нужна только гипотетически;
- дублирует внешний инструмент без преимущества;
- усложняет основной путь;
- требует несуществующего бизнес-процесса;
- не имеет владельца;
- не имеет данных для проверки результата;
- может быть выполнена вручную при малом объёме.
