# User Flow — покупка «Волчья Хватка»

## 1. Основной сквозной путь

Главная → Комплект → Форма → Оплата → Спасибо → Письмо → Админка → Обработка →
Отправка → Получение

Это основной коммерческий сценарий MVP. Интерфейс, API, база данных, аналитика и
административная панель должны поддерживать его без необязательных промежуточных
шагов.

## 2. Принципы пути

- Покупателю не нужна регистрация.
- Для двух основных комплектов не используется классическая корзина.
- От первого экрана до формы ведёт одна главная CTA.
- Выбранный комплект передаётся в форму автоматически.
- Цена и итог повторно рассчитываются сервером.
- Заказ создаётся до перехода к оплате.
- Переход на страницу благодарности не считается подтверждением оплаты.
- Покупатель всегда получает понятный результат и номер заказа.
- Администратор видит заказ независимо от успешности оплаты.
- Каждый статус отражает реальный этап обработки.

## 3. Главная

### Цель пользователя

Понять, что предлагает бренд, убедиться в доверии и перейти к выбору комплекта.

### Пользователь видит

- логотип и навигацию;
- главный оффер;
- изображение тренировочных шашек;
- подтверждённые показатели доверия;
- CTA «Выбрать комплект»;
- вторичную ссылку на видео;
- основные информационные секции ниже первого экрана.

### Основное действие

Нажать «Выбрать комплект».

### Системное поведение

- Переход или плавная прокрутка к секции основных комплектов.
- Фиксация события `hero_cta_click`.
- Сохранение UTM-параметров в безопасном клиентском контексте до создания
  заказа.

### Ошибки

Статическая и серверно отрендеренная часть главной остаётся доступной даже при
недоступности аналитики. Ошибка аналитики не блокирует путь.

## 4. Комплект

### Цель пользователя

Сравнить два основных предложения и выбрать подходящее.

### Пользователь видит

- комплект «Старт»;
- комплект «Мастер»;
- изображения;
- состав;
- преимущества;
- актуальные цены;
- старые цены, если они корректно заданы;
- понятную кнопку покупки у каждого комплекта.

### Основное действие

Нажать «Купить комплект» у выбранного товара.

### Системное поведение

- Фиксация `product_view` при фактическом просмотре карточки.
- Фиксация `product_select` после выбора.
- Открытие формы с уже выбранным Product.
- Фиксация `order_open`.
- Передача только идентификатора или slug товара, но не авторитетной цены.

### Ограничения

- Скрытый или неактивный товар нельзя выбрать.
- Если состояние товара изменилось после загрузки страницы, сервер сообщает об
  этом до создания заказа.
- Дополнительные товары не отвлекают от двух основных комплектов.

## 5. Форма

### Цель пользователя

Передать данные для заказа и выбрать доставку.

### Пользователь видит

- выбранный комплект;
- количество;
- ФИО;
- телефон;
- email;
- город;
- способ доставки;
- адрес или пункт получения, если требуется;
- комментарий;
- итоговую сумму;
- согласие с юридическими документами;
- кнопку оформления.

### Mobile

Форма занимает весь экран. Выбранный товар и итог остаются понятными без
возвращения к карточке.

### Основное действие

Нажать «Оформить заказ».

### Проверки

- Обязательные поля проверяются на клиенте для удобства.
- Все данные повторно проверяются на сервере.
- Телефон и email нормализуются.
- Сервер получает актуальный Product.
- Сервер повторно получает цену и рассчитывает итог.
- Клиентская сумма не считается доверенной.
- Применяется rate limit.
- Повторная отправка блокируется на время запроса.

### Успешный результат

В одной транзакции создаются:

- Order;
- один или несколько OrderItems;
- snapshot названия, slug и цены;
- публичный номер заказа;
- UTM-контекст.

Начальный статус заказа — `NEW`.

После успешного создания фиксируется `order_submit`.

### Ошибки

**Ошибка поля:** показывается рядом с полем, остальные значения сохраняются.

**Товар недоступен:** пользователь возвращается к выбору с ясным сообщением.

**Цена изменилась:** показывается актуальная цена, требуется явное повторное
подтверждение.

**Ошибка сервера:** заказ не дублируется, пользователь получает безопасную
возможность повторить отправку.

## 6. Оплата

### Цель пользователя

Оплатить созданный заказ.

### Системное начало

- PaymentService создаёт попытку оплаты.
- Payment связывается с Order.
- Сумма берётся из сохранённого заказа.
- Создаётся уникальный idempotency key.
- Order переводится в `AWAITING_PAYMENT`.
- Фиксируется `payment_start`.

### Mock-режим

До подключения реальных ключей используется mock-провайдер. Он имитирует
проверенный успешный или неуспешный результат без внешнего списания.

### Робокасса

После настройки пользователь переходит на защищённую страницу провайдера.
Параметры формируются сервером.

### Подтверждение

Оплата считается успешной только после доверенного callback:

- проверена подпись;
- совпадает идентификатор заказа;
- совпадает сумма;
- событие не обрабатывалось ранее;
- Payment переводится в `SUCCEEDED`;
- Order переводится в `PAID`;
- устанавливается время оплаты;
- фиксируется `payment_success`.

Изменение Payment и Order выполняется атомарно.

### Ошибки

**Отмена покупателем:** Payment получает `CANCELLED`, заказ сохраняется.

**Отказ:** Payment получает `FAILED`, покупатель может повторить оплату новой
попыткой.

**Нет callback:** success-страница не меняет статус на `PAID`; система ожидает
подтверждение или предлагает проверить позже.

**Повторный callback:** возвращается безопасный успешный ответ без повторного
изменения заказа.

## 7. Спасибо

### Цель пользователя

Получить подтверждение результата и понять следующий шаг.

### Для подтверждённой оплаты

Показываются:

- благодарность;
- номер заказа;
- состав;
- сумма;
- статус «Оплачен»;
- информация о дальнейшем подтверждении и доставке.

### Для заявки без подтверждённой оплаты

Показываются:

- подтверждение создания заказа;
- номер заказа;
- текущий честный статус;
- предложение повторить оплату или дождаться проверки;
- контакт для вопросов.

### Ограничения

- Страница не раскрывает персональные данные по одному угадываемому номеру.
- Данные берутся из серверно проверенного контекста.
- Текст «Оплачено» показывается только при статусе `PAID`.
- Обновление страницы не создаёт повторный заказ и платёж.

## 8. Письмо

### Покупателю

После создания заказа отправляется письмо с:

- подтверждением заявки;
- номером заказа;
- составом;
- суммой;
- текущим статусом;
- инструкцией по оплате или подтверждением оплаты;
- контактами для вопросов.

После подтверждённой оплаты может отправляться отдельное платёжное письмо, если
первое было отправлено до callback.

### Администратору

Отправляется уведомление о новом заказе:

- номер;
- имя;
- телефон;
- email;
- товар;
- сумма;
- способ доставки;
- ссылка на карточку заказа в админке.

### Системное поведение

- Отправка email не удерживает транзакцию создания заказа.
- Ошибка email не удаляет заказ и не меняет успешный результат формы.
- Ошибка журналируется.
- Допускается повторная отправка.
- В дальнейшем NotificationService может получить Telegram-адаптер.

## 9. Админка

### Цель администратора

Увидеть новый заказ и получить все данные для обработки.

### Новый заказ

Заказ появляется в списке сразу после создания, даже если оплата ещё не
завершена.

Администратор видит:

- номер;
- дату;
- статус заказа;
- статус оплаты;
- покупателя;
- контакты;
- состав;
- суммы;
- доставку;
- комментарий;
- UTM при необходимости;
- журнал событий.

### Защита

- Требуется административная сессия.
- Неавторизованный пользователь не видит заказы.
- Просмотр и изменение критичных данных фиксируются по правилам аудита.

## 10. Обработка

### Цель администратора

Проверить заказ, связаться с покупателем при необходимости и подготовить товар.

### Действия

- проверить подтверждение оплаты;
- проверить данные доставки;
- уточнить недостающую информацию;
- добавить внутреннюю заметку;
- перевести оплаченный заказ в `PROCESSING`;
- подготовить изделие и материалы курса.

### Правила статуса

- `NEW` — заявка создана.
- `AWAITING_PAYMENT` — ожидается подтверждение.
- `PAID` — оплата подтверждена.
- `PROCESSING` — заказ принят в работу.

Неоплаченный заказ не переводится в обработку как оплаченный без отдельного
подтверждённого основания.

Каждая смена статуса записывается в AuditLog.

## 11. Отправка

### Цель администратора

Передать физический товар выбранной службе доставки и зафиксировать отправку.

### Данные отправки

- способ доставки;
- трек-номер, если доступен;
- дата отправки;
- служебное примечание;
- ссылка отслеживания, если она безопасно формируется.

### Системное поведение

- Order переводится в `SHIPPED`.
- Время отправки сохраняется.
- Покупателю отправляется уведомление.
- При наличии трек-номера он включается в письмо.
- Смена статуса фиксируется в AuditLog.

### Ограничения

- Статус `SHIPPED` не устанавливается без фактической передачи заказа.
- Трек-номер валидируется по базовым ограничениям.
- Исправление трек-номера журналируется.

## 12. Получение

### Цель

Зафиксировать завершение заказа после получения покупателем.

### Подтверждение

В MVP получение может быть подтверждено:

- администратором по данным службы доставки;
- администратором после связи с покупателем.

Автоматическая интеграция с доставкой не добавляется без отдельного требования.

### Системное поведение

- Order переводится в `COMPLETED`.
- Сохраняется дата завершения.
- Смена статуса фиксируется в AuditLog.
- Заказ остаётся доступен в истории.

### После получения

Запрос отзыва может быть добавлен позднее через NotificationService, но не
является обязательной функцией MVP.

## 13. Сводная карта статусов

| Этап пути | Order status | Payment status |
|---|---|---|
| Форма успешно отправлена | `NEW` | отсутствует |
| Оплата инициирована | `AWAITING_PAYMENT` | `PENDING` |
| Оплата подтверждена | `PAID` | `SUCCEEDED` |
| Оплата неуспешна | `AWAITING_PAYMENT` | `FAILED` или `CANCELLED` |
| Заказ принят в работу | `PROCESSING` | `SUCCEEDED` |
| Товар отправлен | `SHIPPED` | `SUCCEEDED` |
| Товар получен | `COMPLETED` | `SUCCEEDED` |
| Заказ отменён | `CANCELLED` | соответствует фактическому результату |

Payment status не выводится из Order status автоматически. Они связаны, но
хранят разные факты.

## 14. Переходы статуса заказа

Разрешённый основной путь:

`NEW` → `AWAITING_PAYMENT` → `PAID` → `PROCESSING` → `SHIPPED` → `COMPLETED`

Дополнительные допустимые переходы:

- `NEW` → `CANCELLED`;
- `AWAITING_PAYMENT` → `CANCELLED`;
- `PAID` → `CANCELLED` только через контролируемую административную процедуру;
- `PROCESSING` → `CANCELLED` только с обязательной причиной.

Обратные переходы запрещены по умолчанию. Исправление ошибочного статуса требует
отдельного административного действия, причины и AuditLog.

## 15. Аналитические события

| Этап | Событие |
|---|---|
| Главная | `hero_cta_click` |
| Просмотр комплекта | `product_view` |
| Выбор комплекта | `product_select` |
| Открытие формы | `order_open` |
| Создание заказа | `order_submit` |
| Начало оплаты | `payment_start` |
| Подтверждение оплаты | `payment_success` |

Событие фиксируется только после фактического действия или подтверждённого
результата. Аналитика не содержит полные персональные данные покупателя.

## 16. Ответственность слоёв

### UI

Показывает текущий шаг, собирает ввод, отображает состояния и не принимает
финансовые решения.

### API

Валидирует транспортные данные, применяет rate limit и вызывает один прикладной
сценарий.

### Services

Координируют создание заказа, оплату, уведомления и смену статусов.

### Repositories

Сохраняют и получают Order, OrderItems, Payments и AuditLog.

### Payment Provider

Формирует и проверяет провайдерские данные, но не меняет заказ напрямую.

### Notification Provider

Доставляет письмо и сообщает результат отправки, но не определяет статус заказа.

### Admin

Выполняет физическую обработку и подтверждает фактические этапы после оплаты.

## 17. Критерии готовности пути

Сценарий считается готовым, когда:

- главная открывается на desktop и mobile;
- CTA ведёт к двум комплектам;
- кнопка товара открывает форму с выбранным Product;
- сервер не доверяет клиентской цене;
- заказ и позиции создаются атомарно;
- заказ виден в админке до оплаты;
- mock-оплата переводит заказ в `PAID`;
- реальный callback можно обработать только один раз;
- страница благодарности показывает честный статус;
- email-ошибка не теряет заказ;
- администратор проводит заказ через обработку и отправку;
- завершённый заказ сохраняется в истории;
- каждый критичный переход покрыт тестом и AuditLog.
